# M2–M3：事件调度与长期自治技术方案

适用阶段：M2 基础调度；M3 Goal/外部事件/主动执行

## 1. 实施边界与输入

**目标**：将可恢复的时间实例与可信事件映射为有范围、有预算、可撤销的长期工作。

**前置条件**：Task/Run/Outbox/唯一 Owner 与 Claim 接口可用；外部 Source 接入前已具备身份和接收范围校验。

**对应工作包**：`RUNTIME-004`、`DOT-003`、`DOT-005`。工作包的定义与阶段 Gate 统一见总体规划。

**共用合同**：[领域接口](contracts/domain.ts)、[数据库结构](contracts/schema.sql)、[协议能力矩阵](contracts/protocol-capabilities.json)。本专题定义所属领域的语义，直接引用共用合同，不复制第二套 Schema。

**协作边界**：派工与提交对账见[M2 Runtime](02_M2_工作台与持久执行.md)，用户输入/记忆关联见[M3 对话与记忆](03_M3_单主聊天_上下文与个人记忆.md)。

## 2. Source、Subscription 与事件准入

Source Adapter 由可信配置绑定连接、Dot、接收范围和身份；Webhook 校验签名/投递来源，轮询在保存事件与推进游标时保证崩溃可恢复。设备事件需要配对身份和防重放。凭据保留在受保护连接中，Actor 身份不从正文中的用户名推断。

IncomingTrigger 是不可变事实，按 `(source_id, source_event_id)` 唯一；SQL 拒绝 UPDATE。载荷可按隐私政策删除，保留的 Hash/最小审计也受保留规则管理；“不可变”不意味着永不允许遗忘。接收时记录验证引用、原始载荷引用和接收/发生时间。

| Subscription purpose | 能做什么 | 必须校验 |
|---|---|---|
| `context_only` | 投递相关上下文 | 可见性、来源、大小与保留期；不自动唤醒或授权 |
| `wake` | 唤醒已授权工作，重新检查当前条件 | Task/Goal 状态、Mandate、Policy/Privacy、预算及投递幂等 |
| `actionable` | 进入已有范围内的操作评估 | 仍经 Admission 与 Dispatcher；具体 Action 单独审批 |

匹配 Subscription 只确定投递对象；不能把 Thread 中所有评论当用户指令。多 Task 命中时按 `(trigger_id, task_id, delivery_kind)` 保存 Delivery，分别 Claim/Acknowledge/重试；不共享私有上下文。忽略自己的回声，关联 Bot/CI 有独立规则和频率上限。

Admission 先确定是否具有可行动的来源与范围，再使用模型判断相关性。新建、关联、忽略和澄清均记录理由与候选；超出当前 Mandate 的目标必须走新的可信命令授权。停止 Goal/Task 时同步停用对应 Subscription、Schedule、待派工及未消费授权。

## 3. Goal、Schedule 与主动执行

### 3.1 目标与计划提交

Goal 有成功条件、约束、截止时间、关联 Task、计划版本、复审时间、范围和预算。Planner 提出 Plan Diff；确定性服务检查依赖 DAG、能力、截止时间、配额及取消条件，并在事务内提交 Task/Schedule/Subscription 变更与 Outbox。模型不能仅用“我会记得”宣称已经安排，必须返回持久化对象 ID。

`Goal.version` 表示目标状态/约束版本，`plan_version` 表示已接受计划。用户修订先使旧计划的待派发项失效，再运行新的规划；新计划尚未形成时保持 `needs_review` 或等待复审，不能继续按失效条件执行。已经派发的外部动作保存结果，不能通过版本更新宣称已回滚。

### 3.2 三种不同的时间对象

- **Schedule**：可修改的一次性/Cron 计划，保存 IANA 时区、表达式、版本和下一执行时间。
- **Occurrence**：某版本计划在一个确定 UTC 时刻的实例，唯一键为 `(schedule_id, scheduled_at_ms, schedule_version)`。
- **IncomingTrigger**：实例被兑现后持久化的不可变输入事件；事件到达时间不代替计划时刻。

Occurrence 的 `waiting_host` 是计划实例状态，不是 Task 的新枚举。到期时在短事务内校验 Schedule/Goal/Task 的当前有效性，创建或读取唯一实例，保存输入事件与 Outbox，再推进下一时刻；失败可重跑事务。实例 `enqueued` 表示输入已可靠进入处理链，不代表业务 Task 完成。

当前内部计划 API 使用同一 Revision 6 账本，支持创建、暂停、取消、恢复和替换；Command Key/规范输入 Hash 去重，Task/Schedule CAS 分别校验。创建只接受有可复用输入的 queued Task，原子转为 waiting_trigger；同 Task 最多一个 active/paused Schedule。新计划保存 `contractVersion=2`、输入 Hash、Policy/Privacy/Goal 版本、日历基线和明确派发目的；旧合同 1 只保留 queue_only 权限。未知旧合同先暂停、只显示需替换元数据；不猜测新授权。一次性计划必须有晚于计划时刻且不超过一天的期限。默认唤醒只恢复 queued；一次性只读任务可由用户明确选择 execute_readonly_once，Cron/代码任务自动执行拒绝。桌面提供安排/暂停/恢复/改期/取消、派发状态/Run 链接和最近 100 实例；Main 存活期间每秒有界推进/消费；关闭窗口保留 Owner，重开复用状态，显式退出应用停止。尚未接独立 Daemon。

到期实例、可信内部 Source 的不可变 IncomingTrigger、逐 Task wake Delivery、Task 事件 Outbox 和下一时刻在单个事务保存。Source ID/身份绑定由 Host 固定，接收时间来自可信可注入时钟；内容不能自称内部时钟。投递消费在另一个短事务再次校验 Source、计划版本/期限、输入和授权基线，只对 waiting_trigger 且无活跃/未知 Run 的 Task 入队并确认一次。计划及 Task 暂停/取消同事务撤销未消费实例/投递；Task 完成也同步停止计划。人工恢复任务不重新启用原计划。已经确认的投递保留事实，不当作撤回执行。入队消费者没有模型或外部效果；明确自动派发再通过独立的 Host 准入与原 Execution Gateway 执行。

一次性只读自动执行使用 Host 从 Trigger ID 派生的固定 Run Key，入队事件保存的 Task 版本作为 CAS，不能查询最新版本替换。创建 Run、预算预留、来源关联事件与 Prompt Manifest 引用在同一 Owner 事务；随后复用原 ForegroundExecution/Intent/原生策略流程，Renderer 不获得按 Trigger 派发的接口。任一已创建 Run 都永久阻止同实例再次自动发送，包括失败、Owner 恢复及 Unknown；领取已提交但还没发送的崩溃也保持未知，不推测可安全再发。事务未提交则整组回滚后仍可第一次领取。共享执行忙/预算不足可以等待，版本/期限/来源/权限变化则明确停止；每轮最多查看 20 个候选，Root 候选有界并轮转避免饥饿。自动执行不跳过 Task 审查；读模型回复不等于业务验证完成。

### 3.3 补偿、重叠与时钟规则

| 情况 | 默认规则 |
|---|---|
| 监控类 Cron 错过多次 | `coalesce`，合为一个最新检查；保留被跳过实例的最小记录 |
| 过期一次性提醒 | 根据期限与用户选择 `skip` 或一次补发，不无期限补跑 |
| 明确需要逐期处理 | `bounded_catch_up`，每轮最多配置的 1–10 次，超过部分等待下一轮或丢弃并记录 |
| 前一 Run 尚未结束 | `skip` 或 `coalesce`；不默认并发跑同一 Task |
| DST 重复当地时刻 | 默认只取较早一次；需要两次必须显式配置，两次用不同 UTC 实例区分 |
| DST 不存在当地时刻 | 默认跳过该当地实例；不隐式改到其他小时 |
| 用户改期/暂停/取消 | 更新 Schedule 版本，未派发旧实例标取消；派发前再次校验当前版本 |
| 主机休眠或时钟跳变 | 唤醒后以 UTC 重算到期与补偿；进程内超时采用单调时钟，Lease 使用可信 Runtime 时间并处理跳变 |

Cron 计算锁定 `cron-parser 5.10.3` / `luxon 3.7.2`，五段数字字段、分钟分辨率，支持 2020 至 2100 年（不含）；宏、随机 Hash、秒、L/#、文字星期及同时限制日期/星期拒绝。库仅枚举合成当地日历，实际 IANA 偏移映射负责缺失跳过、重复较早一次；反向查询需考虑重复区间的完整较早时段。单次最多 512 个候选，搜索超限或无未来实例返回错误。计划保存计算策略及 Runtime 的 ICU/tz 基线，基线变化时停止推进并重新确认。Node/Electron 实际 tz 版本及独立 UTC 枚举结果见进展记录，不用库的 DST 支持声明替代实测。条件型价格/状态监控是 Source 或定时检查 Task，条件命中后产生事件；不把任意 LLM 判断装进不可恢复的内存定时器。

当前 coalesce/skip 对多年错过跨度保存首个跳过实例及范围事件，不逐分钟制造无界行；最新实例另存完整 Occurrence。bounded_catch_up 每个计划每轮最多 1–10 项，保留下一未处理时刻；Overlap coalesce 最多一个最新 waiting_host，skip 明确标记跳过。每轮最多 20 个计划，消费最多 20 个投递。时钟回退不回退持久游标；恢复 Owner 不重发已经保存的输入。Unknown、已排队、活跃执行或待审查都不自动恢复，停止结果与任务验证语义保持独立。

主动引擎三层：L0 去重/白名单/有效期/速率 → L1 相关性与证据判断 → L2 Planner/执行。大部分等待时间不调用 LLM。Goal 完成或取消时，相关未执行计划、订阅、自动唤醒及通知订阅在同次 Domain 事务中停止；不推迟到设备阶段。

## 4. 预算、资源与通知

预算分为 Token、估算费用、并发 Run、工具次数、CPU/内存/时长、Browser/PTY 数、存储和事件速率。美元估计与订阅额度分别显示；已经发生的模型成本不能因取消撤回。

派工前在同一短事务中对所需 Budget Bucket 做条件预留，并领取并发令牌：

```sql
UPDATE budget_buckets
   SET reserved_units = reserved_units + :reservation
 WHERE bucket_id = :bucket_id
   AND limit_units - consumed_units - reserved_units >= :reservation;
-- affectedRows=1 后才能写 reservation 并提交；任一桶不足则整组回滚。
```

结算将实际 Usage 写入账本并释放未用预留；Usage 未知保持保守预留并对账。实际消耗可能超出估计，必须如实记录超额并停止新派发，数据库不能因额度 CHECK 拒绝记录已发生费用。目标是限制新工作与可控步长，不承诺精确零超支。

当前本机策略持久化于 Revision 6：默认 UTC 日周期 1,000,000 Token、每 Run 预留 32,000、最多一个前台 Run；这是本地准入参数，不是服务商套餐额度。Run/Task/Fence/Workspace 领取和全组预算条件预留在同一事务；任一全局/Goal 桶不足则整体回滚。缺可信价格时美元估计为 unknown；存在要求估价的费用桶则拒绝派发，不假设成本为 0。报告增量超过预留会扩大占用，结束仍记录超额并阻止后续准入，不承诺当前上游调用的硬 Token 上限。

用量只接受绑定 Run/Thread/Turn 的 `thread/tokenUsage/updated.tokenUsage.total`，按累计高水位计算，不叠加重复快照或 last。新 Thread 基线为 0，复用有记录 Thread 的已知基线；旧 Thread 无基线、零/回退/非法计数、缺失 Usage 和中断 Unknown 保留预留，不当作已知零。确认没有发送模型 Turn 才允许零 Token。停止结果和用量结果独立，历史对账不编造 Usage；确认 Run 结束可释放并发占用，但未知用量仍占预算。语义参考 [OpenAI Token Accounting](https://github.com/openai/symphony/blob/main/elixir/docs/token_accounting.md)，以锁版 DTO 与实际接口核对。

`budget_policies/run_usage/thread_usage` 与预留的实际值/结算 Hash 在同一 SQLite；2/3→4 先保存含 WAL 的一致性私有备份并验证，失败不更新 Revision 或留下半套列。GUI 显示共享预算、报告 Token、当前/未知预留、活动 Run 和美元未知，没有 Renderer 改预算或手填 Usage 的能力。真实模型与合成计数分别记录；上游报告不是订阅账单，未知历史周期预留不悄悄删除。

预算、Run、子 Agent、Browser 和重试共享资源准入，不能分别读到同一份余额再各自支出。任务退出在事务性 Finalize 中释放可释放令牌；失联先核查真实进程，未知占用不立即重复发放。

通知独立于执行：稳定去重键、静默时段、每日噪声预算、失败熔断、用户订阅和取消。后台常规检查无变化则静默，重要结果/失败/补问有明确归属。发送通知本身也保存派发与回执，设备多端同步不形成重复任务。

## 5. 分阶段实施与交付

M2 先实现内部 Scheduler Source、once/cron、Occurrence、Misfire、Overlap、Outbox 唤醒和基础预算；不要求先实现 Goal Planner、GitHub Webhook 或模型相关性判断。时钟可注入，Cron/Timezone 依赖锁定，并保留每个实例的计划版本和处置结果。

M3 再加入 Goal/Plan Diff、外部 Adapter、Subscription/Mandate、L0/L1/L2 与通知。外部事件可从受支持的鉴权轮询起步，不为演示额外暴露未经认证的公网入口。命中订阅后的 Delivery 与新建目标的 Admission 有明确区别。

暂停/改期/取消的 Domain 事务先使旧条件失效，再通过 Outbox 协调实际执行端。计划已保存、Occurrence 已入队、Run 已执行和通知已送达分别展示；任意一项 Unknown 都不能补写成成功。

对外提供 Schedule/Occurrence、IncomingTrigger/Delivery、Goal Plan Diff 与预算准入接口。交给设备入口的是已持久化结果和受保护批准请求，不让设备复制一套 Scheduler。

## 6. 开发验证要求

以下只规划 M2/M3 必须覆盖的验证范围与验收证据。具体输入、步骤、Fixture、故障注入方式和自动化实现，在对应工作包真实开发时并行细化。当前不宣称已经形成完整用例库或通过应用验收。

| 验证方向 | 必须覆盖 | 验收证据要求 |
|---|---|---|
| M2 计划实例 | once/cron、Occurrence 唯一键、重投、DST、休眠/时钟跳变 | 计划时刻/版本/处置记录，补偿次数有界 |
| M2 资源准入 | 并发预算竞争、未知用量、超额结算与进程资源回收 | 余额/预留/实际消耗/令牌记录 |
| M3 来源与投递 | 身份校验、伪造/重复/乱序、Bot 回声、多目标与订阅用途 | 可信来源、逐 Task Delivery、无扩权/循环唤醒 |
| M3 Goal/计划变更 | 新约束、Plan Diff、依赖、暂停/取消/完成后的清理 | 当前计划版本和旧实例/订阅失效证据 |
| M3 主动执行/通知 | 无关事件过滤、条件命中、静默/去重/频率与用户取消 | 决策、动作和通知分开计数与确认 |
| 长期闭环 | 真实 Task 派工、等待、重启、修订与终止 | 同一 Goal/Task 链及可信结果，不依赖常驻 LLM |

每项实际验证记录正常/失败/拒绝/恢复结果，区分真实组件、Stub、模拟器和外部阻塞；执行状态与证据格式遵循[总体规划](00_总体架构与开发规划.md)的开发验证规则。
