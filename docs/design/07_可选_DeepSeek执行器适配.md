# 可选：DeepSeek 执行器适配技术方案

适用阶段：M2 后的隔离实验；非 M0/M1 Gate  
实施状态：技术方案与验证要求已定义；具体用例在真实开发时与实现并行细化，应用结果另行记录。  
总体入口：[总体架构与开发规划](00_总体架构与开发规划.md)

## 1. 实施边界与输入

**目标**：在稳定产品控制平面下评估 DeepSeek Harness/DSH，复用领域思想并验证可替换执行器的实际边界。

**前置条件**：Codex 主线与 Execution Gateway 已可运行，隔离 Fixture、事件/Action 账本和可比较的验证规则具备。

**对应工作包**：`DSH-001`。工作包的定义与阶段 Gate 统一见总体规划。

**共用合同**：[领域接口](contracts/domain.ts)、[数据库结构](contracts/schema.sql)、[协议能力矩阵](contracts/protocol-capabilities.json)。本专题定义所属领域的语义，直接引用共用合同，不复制第二套 Schema。

**协作边界**：任务/Intent/未知结果语义见[Runtime 方案](02_M2_工作台与持久执行.md)，Source 与授权范围见[事件自治方案](04_M2_M3_事件调度与长期自治.md)，实际强制边界见[可信执行方案](05_M2_M3_可信执行与ComputerUse.md)。

## 2. DeepSeek 与执行器扩展

模型、Harness 和产品控制平面是独立选择：使用某个 DeepSeek 模型不等于采用其 Harness；采用 Harness 也不自动具备 Personal Memory、可信凭据或设备平台。

DSH Super-Agent 的 Source、Admission、Mandate、Task/Assignment 分层和 Subscription 可作为设计参考。项目自己的 Task/Run、身份、撤销与回执合同保持稳定。公开 DSH 研究原型面向单仓库协作，命令执行及部分交付要求不能直接作为本产品的安全机制。

实验 Adapter 仅在隔离仓库完成 `Issue→Task→Run→PR→Review` 对照：固定提交与许可，测量成功率、耗时、Token/费用、人工介入、失败恢复和权限拒绝。实验不参与 M0/M1 Gate。只有相同工作负载下的质量、恢复与安全证据通过后，才能对指定能力启用；不能在现有未知结果期间切换执行器重跑。

候选上游定位：Codex CLI `0.163.0` 的生成类型；DSH Prototype `6337fc823ce20251c8de8085948165c81aaa701e`；DeepSeek Harness `ce7073d51254c26cd63b22a60835b8f948deb447`（默认分支 `master`）。这些是可定位的研究输入，不代表已经构建或运行兼容。

## 3. 适配边界与数据映射

| 项目合同 | Adapter 必须提供的行为 | 核验方式 |
|---|---|---|
| Task / Run | 仍由本项目持有业务状态与派工窗口；DSH Session/Assignment 通过映射关联 | 任务 ID 不变、无第二套权威状态 |
| prepare / submit | 保存输入、Grant、版本与 Intent，确认提交被接受后绑定真实执行 ID | 逐个 SDK/进程调用锁版验证，不假定存在同名 DSH RPC |
| 观察 / 结果 | 将真实工具/执行事件映射为当前 Run 和证据 | 不能将自然语言“已完成”映射为完成收据 |
| interrupt / reconcile | 明确停止确认、在途状态与核查能力 | 无法核查就保留 Unknown，不退回 Codex 盲重跑 |
| 工具与权限 | 以保护域、外部沙箱和受管 Gateway 承担强制限制 | 原型中无逐步审批的命令路径不能直接带入真实账号环境 |
| Memory / Context | 仅接收当前 Task 的来源化 Bundle | 不复制整份主聊天、凭据或不相关私人记忆 |

每个 Run 固定 executor_kind 和必要版本/配置；执行途中不因模型错误切换引擎重新提交。中止且对账完成后，由新的受控 Run 选择执行器。模型 Provider 与 Harness 分开配置，使用 DeepSeek 模型不自动切换业务 Runtime。

## 4. 实验步骤与采用条件

固定两个上游提交、许可和依赖 → 隔离构建/接口探测 → 单仓库 Issue 事件 → Task/Run → 修改与验证 → PR/Review 模拟 → 崩溃/重复事件/撤销/未知结果 → 与 Codex 对照。

比较时固定同一任务 Fixture、输入、可用工具、验证器、资源预算与权限；分别记录模型差异和 Harness 差异，不能把更换模型造成的变化全部归给执行架构。记录成功率、样本数、耗时/Token、人工介入、恢复与拒绝结果，不预设必然更优。

只有受保护的执行、可靠映射与足够样本的对照结果满足目标能力，才为该能力启用 Adapter。若 SDK、许可、身份或核查能力不足，保持实验关闭，不影响 Codex 主线验收。

## 5. 开发验证要求

以下只规划 可选实验 必须覆盖的验证范围与验收证据。具体输入、步骤、Fixture、故障注入方式和自动化实现，在对应工作包真实开发时并行细化。当前不宣称已经形成完整用例库或通过应用验收。

| 验证方向 | 必须覆盖 | 验收证据要求 |
|---|---|---|
| 基线与接口 | 固定源码/许可/构建、SDK/进程能力和缺失接口 | 可复现环境与实际能力，不用虚构 RPC |
| 业务映射 | Source→Task/Run→执行→PR/Review、事件关联与完成判定 | 同一 ID/证据链，无第二套业务权威 |
| 故障与权限 | 停止、提交未知、重投、工具旁路与数据范围 | 核查或 Unknown，实验不带入真实私人账号 |
| 对照与采用 | 同一 Fixture/验证器/工具/权限/预算下对照 Codex | 样本数、成功/成本/人工介入/恢复，模型与 Harness 差异分开 |

每项实际验证记录正常/失败/拒绝/恢复结果，区分真实组件、Stub、模拟器和外部阻塞；执行状态与证据格式遵循[总体规划](00_总体架构与开发规划.md)的开发验证规则。
