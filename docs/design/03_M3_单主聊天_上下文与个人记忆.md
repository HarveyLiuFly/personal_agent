**对应工作包**：`DOT-001`、`DOT-002`、`DOT-004`、`PROMPT-001`。工作包的定义与阶段 Gate 统一见总体规划。

## 2. 单主聊天、路由、Focus 与多动作

### 2.1 接收与路由顺序

`persist message → decide → validate → commit decision/operations/links/focus/outbox → dispatch → persist result → project feed`。

Message ID 由客户端创建并在重发时复用。相同 ID、相同 Hash 返回既有状态；相同 ID、不同内容拒绝冲突。首次落库可先提交；恢复 Scanner 查找尚无有效 Decision 的消息。

Router 是无副作用 Decision Service，仅输出候选范围内的动作和对象。优先级：可信 UI 显式对象 → 有效 Pending Interaction → 用户建立的 Focus → 标题/别名/实体/项目路径检索 → 结构化模型 → 确定性 Dispatcher。

支持 `CHAT/CREATE_TASK/CONTINUE_TASK/UPDATE_TASK/QUERY_TASK/PAUSE_TASK/CANCEL_TASK/CREATE_GOAL/CLARIFY`。一句话多动作表达为 `operations[]`，不另造一个具有隐式执行权的 MULTI_ACTION 工具。显式 Task ID 解决归属，不自动决定动作；查询默认读取 Registry，不启动修改任务。

模型输出按 JSON Schema 验证；现有 Task ID 只能来自授权候选。Dispatcher 生成并持久化 Operation ID，检查目标所属 Dot、版本、状态、风险、依赖与配额。模型置信分数只作排序参考。对“把那个停掉”“选 B”等存在多个合理对象时保存澄清项并等待明确回答。

当前首个切片使用 Schema 6 的同一 conversations/messages/router_decisions/operations/message_task_links/focus_states/pending_interactions。固定 chat:read/chat:submit 接收已注册项目 ID、客户端稳定 Message ID、文本及 Focus Revision，可选显式 Task/Pending ID；没有模型、SQL、路径或派工参数。一个 Dot 共用 Conversation/Focus，当前视图按所选项目过滤；跨项目 Focus 不成为该项目的默认目标，但其全局 Revision 仍参与 CAS。消息/Decision/QUERY_TASK/Link/Focus 或 Pending 同事务，重发先核对原 Hash，不回写旧 Focus。查询读取 Registry，不依赖物理项目目录，不能据此授予文件访问或执行能力。

首期支持 /query 单目标、/note 讨论记录和中英文状态查询。对象顺序为可信 UI 显式对象、明确文本 Task ID、有效 Focus、唯一标题；未知/多 ID 不回退旧 Focus，同名多候选需明确 Pending ID + 候选 Task，候选版本/项目/有效期重验。选中对象不决定动作；暂停/取消/创建/续接等未接入动作只澄清，无模型或任务效果。无模型回答的讨论记录明确标注，查询结果显示为当时快照。后台事件不改变 Focus。

当前每消息最多 8,192 UTF-16 单元，最近 50 条展示，每条最多 2,000、文本合计 65,536，保留原文并标裁剪；Registry 候选来自最近 100 项可见任务，澄清候选最多 20、近期问题最多 10、有效期 15 分钟。M3 聊天消息最多 10,000 条，超限拒绝而不静默删记录。已过期主聊天问题在读取时转 expired，不触碰其他补问。消息/Task 墓碑过滤快照与 Focus；完整派生关系和物理遗忘仍属后续切片。界面使用纯文本，Pending 选择不清空另一份未提交草稿；保存未确认时复用原 Message ID 核对，Focus/候选变化要求用户刷新后重新选择，不自动套用新版本。

### 2.2 Focus 与纠错

Focus 由用户明确讨论、Task 卡片操作或明确回复建立，带消息 ID、Revision 与建立时间。后台任务结束不更新 Focus。多个等待问题必须用 `pendingInteractionId` 消歧，过期问题或目标已更新时重新校验。

用户更正归属时创建 Correction Event，停止错误目标尚未派发的工作，检查既有副作用，更新关联和 Focus，再构造正确 Context；原始消息和审计链保留。主聊天只展示用户消息、任务级摘要、结果、补问与审批；详细工具流位于 Task Activity。

### 2.3 多动作执行账本

`router_decisions` 保证同一消息只做一次正式规划；`operations` 保证规划中的每项执行可恢复。每项保存输入哈希、目标版本、依赖和 `pending/blocked/executing/completed/failed/cancelled/outcome_unknown` 状态。

- 同库纯变更可在短事务内整体校验和提交；选择整体提交就必须失败时全部回滚。
- 跨服务、需批准或外部副作用按 Operation 分步执行。每项派发前持久化状态，结果提交后唤醒依赖。
- 依赖形成 DAG，拒绝自依赖、循环及跨决策的未授权关系。独立只读项不被另一项审批永久阻塞。
- 已有 Decision 不代表所有 Operation 已完成；重连读取逐项结果，恢复仅处理仍可执行的步骤。
- 外部动作未知时保持该项 Unknown，不进行整组盲重放，也不自动执行补偿性外部写入。

## 3. 上下文、Prompt 与任务连续性

### 3.1 Context Builder

每次构造绑定 Task Version、Goal Plan Version、Privacy Epoch、Checkpoint 和具体来源 Revision。装配完成复查关键版本；预算、权限、截止时间等变化需重建。候选召回、可见性、信任/时效检查与 Token 裁剪分别可观察。

优先保留：上游/宿主执行规则 → 最新用户约束与业务状态 → 当前请求/补问 → 验收与关键决策 → 相关 Episode/Claim → 非关键日志。外部网页、PDF、邮件、无障碍树和截图文字作为带来源的不可信数据，不拼进高权限指令。

Main Context 初期软预算可从 8–16K Token 实验起步；Task Context 依模型与工作量配置。总量由实际 Tokenizer/多模态估计核验，预留工具输出与生成空间，不能把名义模型窗口全部占满。若必要约束超预算，应分解任务或澄清，不静默截断。

FTS/实体标签/最近性与 Focus 是首期检索基线；中文切分需以标注语料测量。只有召回和延迟证明有需要时，再引入多语言 Embedding 与 Reranker。向量分数不提供事实可信度或授权。

### 3.2 Prompt Registry 与工具权限

Git 管理的模块化 Markdown/Manifest 即可起步，按 Policy、Role、Mode 和 Tool Guidance 分类；不在 M1 建设 Prompt CMS。模块包含 ID、内容哈希、适用角色/模式、依赖能力、冲突条件和预算。

角色包含 Coding、Plan、Research、Browser、Computer、Dot Orchestrator、Goal Reviewer、Memory Extractor/Consolidator；模式固定为 `read-only/execution/review/checkpoint-resume/human-takeover-resume`。购物准备等是 Workflow 状态，不新增任意字符串模式绕过合同。

Assembly：读取实际 Capability → 选择必需模块 → 检查冲突/缺失 → 装配来源化 Context → 预算 → 保存 Manifest → 通过锁版支持的 Thread 指令路径提交。保留 Codex Base；敏感 Role 变化创建独立 Thread，或经已验证的 Resume 配置路径变更。Turn Context 刷新不等同于热替换系统指令。

Tool Snapshot 记录实际工具 Schema 与权限哈希。Role 只读必须同时落实到 Sandbox、网络与受控工具；仅在 Prompt 中列出“只能使用 Browser”不能屏蔽内置 Shell。Browser/Computer 工具对模型提供最小接口，隐藏任意 JS/CDP、Desktop Socket 和凭据通道。

### 3.3 Episode、Checkpoint、Compaction 和 Rollover

Episode 按主题/因果与有限长度切分，可多对多关联消息；保存摘要、决策、未决问题和精确来源。来源 ID 必须属于本次输入集合；相关文本存在也不自动证明模型提取的事实成立，关键数字/承诺需核对原文。

Checkpoint 包含任务版本、目标/约束、完成标准、已确认步骤与 Receipt、未完成步骤、待补问、Artifact、工作区/提交与下一预期事件。它由业务状态与证据构建，不把模型自述当执行事实。

Codex Compaction 处理单 Thread 推理历史，Episode 服务处理主聊天检索，Checkpoint 处理业务恢复。Thread 适合当前环境、权限和 Privacy Epoch 时优先 Resume；阶段、工作区、工具边界或隐私资格变化时从有效 Checkpoint 新建 Thread。

`thread_bindings` 保存唯一活动绑定、Generation 与换代原因；自有库不再冗余保存第二个“当前 Thread”权威字段。换代前核对未解决 Action/Intent、当前版本、文件可访问性及所有来源的删除状态。旧绑定可供受控审计，失效绑定不能自动恢复执行。

## 4. Memory、信任与遗忘

### 4.1 存储与检索

Personal Memory 存稳定用户事实与偏好；Task Memory 存计划、决策、产物和恢复状态；Codex Coding Memory 存执行经验。三者分域，并通过有来源、敏感级别和期限的引用连接。

`Entry` 是可追溯源文；`Claim` 是可修订事实；`Evidence` 连接原始消息/文件/Connector；Embedding 是可重建索引。Claim 具有 Trust、现实有效时间、记录时间、版本与 Supersedes 关系。临时任务约束不能覆盖长期偏好，明确用户修正优先于旧推断。

写入流水线：保存来源 → 提取候选 → 信任/敏感性/时效分类 → 核对已有事实和原文 → 确定性校验 → 事务提交 Claim/Evidence → 索引 → 受影响 Goal 复审事件。网页/邮件中关于用户的声明不能自动升级为 `explicit_user`，记忆也不能授予工具权限。

首期使用 SQLite 关键词/FTS 与实体/别名补充中文检索；启用 FTS5 时用事务性 INSERT/UPDATE/DELETE 维护索引，部署时检查已有数据重建。Embedding 必须记录模型/维度/内容哈希；更换模型重建独立索引，不能混查不同维度。后台 Consolidation 单写协调，按来源和事实键幂等，避免每条消息同步调用强模型。

### 4.2 Privacy Epoch 与删除工作流

所有 Context、Episode、Claim、Checkpoint、Manifest、Artifact 和 Thread Binding 关联 Privacy Epoch 与来源 Revision。`derivation_edges` 记录来源到派生产物的依赖。仅比较全局 Epoch 不足以证明内容可用：旧产物需重验来源、删除墓碑和权限，通过后才能生成新的有效产物。

遗忘流程：

1. 可信用户命令确定范围，提升 `dots.privacy_epoch`，写最小化删除墓碑；先阻止相关来源进入新上下文。
2. 遍历依赖边，标记 Claim/Entry、Episode、Context、Checkpoint、Artifact、Feed 缓存和索引无效；使相关 Thread Binding 失去恢复资格。
3. 协调正在运行的 Run 停止后续派发，清理或替换含被删来源的执行上下文。不能让“只清了检索库”的旧 Turn 继续产出并写回记忆。
4. Extractor/Consolidator 在读取和提交前都核对墓碑及 Epoch；并发作业不能复活删除来源。
5. 完成可控本地副本的删除/重建，报告产品不再使用、物理清理和供应商保留策略各自的完成情况。

私人 Context 不默认进入用户共享的 Coding Memory 域。Dot Runtime 采用独立数据域；历史保留和记忆抽取开关只有经过锁版验证才能使用。若无法证明特定运行时会保留哪些派生内容，就限制敏感注入，停止恢复相关 Thread，并如实说明无法完成的清理范围；不依赖 Prompt“不要记住”。

恢复旧备份前合并当前受保护删除日志与 Policy Epoch；若无法取得最新删除日志，则禁止从恢复内容启用记忆和任务。删除日志不能仅依赖同一份可回滚备份保存。

## 5. 开发切片与交接合同

1. 显式 Task 引用、Focus/Pending 与只读查询；先不用模型也可验证主聊天与消息幂等。
2. Task 检索、结构化 Router、逐 Operation 分派和误路由纠正；模型只给候选范围内的提案。
3. Context/Prompt Manifest、Episode、Checkpoint、Rollover；历史压缩与业务事实源分开。
4. Claim/Evidence、检索过滤、Privacy Epoch/派生关系、遗忘与 Runtime 隔离；后台写入必须重新校验来源。
5. 联合 Goal/Scheduler 运行多任务长期场景，验证输入、执行、结果、通知和删除在同一链路内成立。

对下游提供 RoutePlan/Operation、TaskContextBundle/PromptManifest、MemoryEvidence 与受控检索接口。Context Bundle 只有数据与来源，不携带可自行扩权的批准。Memory 与 Goal 间只交换受控事实变更事件，计划最终提交仍由 Goal 服务校验。

验收数据集覆盖中英文项目名、时间指代、多 Pending、临时约束、冲突 Claim 和已删除来源。报告样本数、误路由/澄清类型、召回与成本；不能只汇报总体准确率掩盖破坏性误操作。

## 6. 开发验证要求

以下只规划 M3 必须覆盖的验证范围与验收证据。具体输入、步骤、Fixture、故障注入方式和自动化实现，在对应工作包真实开发时并行细化。当前不宣称已经形成完整用例库或通过应用验收。

| 验证方向 | 必须覆盖 | 验收证据要求 |
|---|---|---|
| 路由与 Focus | 明确对象、歧义、多个 Pending、后台任务完成与查询不派工 | 候选/Decision/Operation 与期望状态，保留样本数 |
| 多动作与纠错 | 逐项前置版本、依赖、部分失败/等待与归属纠正 | 各项执行状态；无整组盲重放 |
| Context/Prompt | 来源、Token 预算、Role/Mode/工具冲突与上下文串扰 | Manifest/工具快照及实际运行权限 |
| 历史与 Rollover | 跨主题历史、来源核对、Compaction、Checkpoint 与 Thread 换代 | 业务 ID 连续、证据可追溯且无 Unknown 重放 |
| Memory 有效性 | 明确用户约束、外部推断、时效、冲突与检索质量 | Claim/Evidence、召回与误判分类，禁止信任升级 |
| 遗忘与长期集成 | 并发抽取、旧 Thread/缓存/备份、与 Goal/Scheduler 的联动 | 删除代与实际后续 Context，无来源复活 |

每项实际验证记录正常/失败/拒绝/恢复结果，区分真实组件、Stub、模拟器和外部阻塞；执行状态与证据格式遵循[总体规划](00_总体架构与开发规划.md)的开发验证规则。
