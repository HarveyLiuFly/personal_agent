# CORE：产品主干收敛重构计划

日期：2026-11-05　依据：[架构/界面/逻辑审查](../reviews/2026-11-05-architecture-ui-logic-review.md)　状态：**计划已确认（2026-11-05，决策见第 7 节），下一步 CORE.0**

## 1. 目标

把项目从“验证流程很重、日常难用的原型”收敛成一个顺手的个人 Agent：

> 打开项目 → 新对话 → Agent 读代码、改代码（需要时请求批准）→ 在右侧审阅变更 → 随时追问、继续或停止 → 重启后接着用。

在这条主干稳定之后，再把目标、定时、记忆这些“个人 Agent”能力挂到对话上。个人 Agent 的统一入口是独立的 **Dot**（类似 Codex 应用里的“your dot”）：普通项目对话不经过路由，路由只在 Dot 这条路径上工作。

**完成后的样子**（与 Codex 应用对齐，见审查 §3.0）：

- 首页三栏：左边按项目分组的对话清单（运行中 / 需批准 / 未读标记），中间对话与输入框，右边扩展面板（审阅 / 文件 / 终端）。
- 一个“对话”就是一个 Codex Thread：多轮上下文完整，可读可写，完成不锁输入。
- 输入框可选模型、推理强度、权限模式（只读 / 自动 / 完全访问）；`@` 引用文件；运行中可追加指令或停止。
- 命令、文件修改、计划在对话里实时出现；审批卡片就在对话里。
- 多个对话可以同时运行；只有“同一工作区的写操作”互斥；运行中随时浏览文件和 Diff。
- 侧栏顶部有独立的 **Dot** 入口：一个全局、常驻的个人 Agent 对话。对它说的话经路由变成可确认的操作（在某个项目里开对话、建定时、记住、建目标），各项目对话和定时结果的进展会回到 Dot。

**不变的底线**（已验证，重构中保持并回归）：

- 真实发送前写 Intent，结果未知不自动重发；重启后核对。
- Electron 沙箱、上下文隔离、CSP；Codex 沙箱；工作区写租约。
- 记忆遗忘覆盖派生内容；备份恢复。
- 锁定 Codex 版本与协议指纹，不手改生成类型。

**冻结范围**：CORE Gate 关闭前不开始 M4/M5，不加新功能；修 bug 与 Linux/macOS 平台问题除外。

## 3. 保留、改造、删除

| 部分 | 处理 | 说明 |
|---|---|---|
| `codex-adapter`（RPC、投影、历史、启动、锁） | 保留并扩展 | 投影改为推送增量；二进制校验启动时做一次 |
| Intent 账本、Unknown 核对、`thread_bindings` | 保留 | 改用协议的 `clientUserMessageId` 作为幂等键，未知时按它自动核对，不再让用户手动“核对这次发送” |

| Context JSON 信封 | 删除 | 用户消息发原文；记忆与项目说明放 `thread/start` 的 `developerInstructions`；来源记录仍写账本 |
| 工作区、终端、工作树、验证、备份服务 | 保留 | 验证从“Node 测试专用”改成可选的项目检查命令 |

| Renderer | 重写外壳，复用组件 | 删除任务页、项目助手页、不可达的工作区页、`ChatRoutePanel` 死代码 |
| `main.ts` 的 27 个 Smoke 开关、16 个探针 | 移出生产入口 | 测试专用入口单独构建 |

## 4. 分阶段工作包

每个工作包结束时应用可以正常使用，并按 AGENTS 规则记录、提交、推送、打 `checkpoint/CORE.x` 标签。工作量是粗估（一个 Agent 加用户验收）。

### CORE.0 基线与护栏（约 1–2 天）

- 一次性格式化（Prettier，`printWidth: 100`）单独提交，只改格式；加 ESLint 与循环依赖检查（先只报告，不阻断）。之后的重构 Diff 才能读。
- 重构前基线：类型检查、构建、17 项设计合同与受影响范围的增量用例，记录实际结果（D5：不跑全量）。
- 证据约定（D4）：Smoke 默认把逐次输出写到 `.local/evidence/`（现有 `PERSONAL_AGENT_EVIDENCE_DIR` 改为默认本地），每个检查点只提交一份脱敏汇总；进展文档保持“阶段记录 + 决策 + 变更”的简明结构。
- 数据保护：用现有备份对 macOS 正式数据做一次备份演练；准备迁移用的数据副本。
- 写出“主干验收”场景（第 5 节）的可执行步骤，作为每个包的回归清单。

验收：格式化提交前后类型检查、构建、合同与增量用例结果一致；Smoke 不再改动 `docs/progress/evidence/` 下已提交的文件。

### CORE.1 运行时：多对话并发与事件推送（约 4–6 天）

- Codex 二进制只在启动时校验一次（哈希 + 版本），后续按文件身份复用结果。
- `ThreadRuntime` 替换单例执行器：一个受限的执行用 App Server 连接上并发多个 Thread；并发上限可配置（默认 3）；“同一工作区的写 Run”沿用现有写租约互斥；每个 Turn 仍先写 Intent。
- 只读操作（目录、历史、文件、Diff、技能、连接检查）走元数据连接，永远不因执行被拒；去掉共享 `active` 标志。Dot 的路由请求也不再因项目对话在运行而卡死（L10）。
- Main → Renderer 事件推送：新增 `pa:event` 通道，事件带序号（对话更新、Item 增量、审批请求、任务/定时变化）；Renderer 断号时重新拉取快照。命令仍走 `invoke`。删除 Renderer 中所有轮询定时器。
- 后台调度改为“下一次到期时间”驱动的单个定时器；路由 `tick` 停止。
- 后台循环统一记录错误到 `userData/logs`，不再空 `catch`。
- 首次启动时由 Host 保持 Codex 索引预热并在界面显示进度（审查 A9）。

验收：两个项目的对话同时运行（合成后端自动化 + 1 次真实运行）；运行中浏览文件、看 Diff、检查连接均成功，0 次 `RUNTIME_BUSY`；窗口 Smoke 连续 5 次通过；空闲时 Main 进程 CPU 接近 0（实测记录）；Unknown 不重发用例全部通过。

### CORE.2 对话模型：一个“对话”替代“助手 + 任务”（约 5–7 天）

- Schema 6 → 7 迁移（迁移前自动备份）：任务即对话，增加模型、推理强度、权限模式、置顶、归档、最近阅读时间；Run 即一轮。旧的主聊天消息与路由记录原样保留，归入 Dot 的历史。
- 发送：用户原文作为 `UserInput`；记忆、项目说明通过 `developerInstructions` 进入；Prompt 来源仍写 `prompt_manifests` 以便审计。
- 项目对话不经过路由：用户消息直接作为该对话的下一轮。
- 现有“项目助手”的路由流程整体剥离为独立的 **Dot** 入口（侧栏顶部），暂时仍按当前项目工作；修复其中的截断（L5）、对页面挂着的依赖（L11）与运行中卡死（L10）。完整的 Dot 改造在 CORE.5。
- 任何对话都可继续；`thread/fork` 支持“从这里新开”；`thread/archive` 支持归档。
- 列表接口分页，按 ID 查找不依赖“最近 N 条”（修 L5/L6）；长内容不再导致回答丢失（修 L13）。
- 发送状态：结果未知时按 `clientUserMessageId` 用 `thread/read` 自动核对；只有确实无法判定时才显示人工处理（修 L7）。

验收：真实对话中追问引用上一轮回答；冷重启后同一对话继续；迁移后的旧任务、旧助手记录可读；60 条消息、30 个对话的列表与查找正确；发送时强杀进程后重启自动核对、不重复发送。

### CORE.3 权限、审批与验证（约 4–6 天）

- 输入框：模型（`model/list`）、推理强度、权限模式。默认“自动”= 工作区可写 + 按需审批；“完全访问”需二次确认且只在本机。项目默认值在设置里。
- 原生审批：命令执行、文件修改、补问（`item/*/requestApproval`、`requestUserInput`）在对话内显示为卡片：允许一次 / 本对话总是允许 / 拒绝；回执写入 `approval_receipts`。
- 运行中追加指令（`turn/steer`）与停止（`turn/interrupt`）放在输入框。
- 验证改为可选的“项目检查命令”（如 `pnpm test`、`pytest`、`go test ./...`），在 Codex 沙箱内运行，结果作为对话中的步骤与徽标；不要求工作区干净；原 Node 测试配置保留为一个预设。
- 对话标题栏选择环境：本地 / 新工作树。

验收（Linux 与 macOS 各一次真实代码任务）：自动模式下模型改文件、运行命令时弹出审批，允许后继续、拒绝后无副作用；停止后进程实际退出；一个 Python 测试项目可以被修改并通过检查命令；审阅 Diff 与验证结果一致。

### CORE.4 界面：三栏外壳（约 5–7 天，可在 CORE.2 接口稳定后与 CORE.3 并行）

- 左栏：项目分组的对话清单，相对时间、运行中/需批准/未读标记；搜索标题与消息；“目标”“定时”两个分组；底部设置与连接状态。
- 中栏：消息、命令（运行中显示最后几行输出）、文件修改、计划按到达顺序流式出现；安全的 Markdown 渲染（不执行 HTML）；审批卡片；加载骨架与空状态分开。
- 右栏：审阅（按文件 Diff，来自 `turn/diff/updated` 与 git；撤销此文件、在编辑器打开）、文件、终端。
- 设置按 个人 / 编码 / 集成 分组（审查 §3.0）：外观（含主题切换）、个性化（记忆、项目说明）、通知、键盘、数据（归档、备份、清理）、用量；配置（模型/推理/权限默认值）、工作树、环境与检查命令；技能/插件/MCP 只读清单；调试（原生历史、连接诊断）。
- 统一状态词表；按钮层级与危险操作确认；每个面板包 ErrorBoundary；文案改为日常语言。

验收：Agent 驱动的原生界面走查（1440/1120/900 宽，深浅色，键盘操作）并截图存证；Renderer 中无轮询定时器；单个面板抛错不影响其他面板。

### CORE.5 个人 Agent 能力挂到对话上（约 4–6 天）

- 定时任务：“在指定时间向某个对话（或新对话）发送这条消息”；常用频率预设，Cron 作为高级选项；结果以未读对话出现；保留“只排队不执行”。
- 目标：侧栏分组，一个目标包含若干对话和完成标准；完成标准由检查命令或对话结果自动判定，不再手填 verificationId。评估是否改用 Codex 原生 `thread/goal/*`。
- 记忆：设置 › 个性化管理；消息上的“记住”；进入 `developerInstructions`；遗忘后从后续对话的指令中消失。
- 资料库（只读）：项目文件、对话产物、Diff 与验证收据。
- **Dot 改造**（对齐 Codex 的“your dot”）：
  - 全局唯一入口，不再按项目分；路由提案中包含目标项目。
  - Dot 自身是一个持久的 Codex Thread：每条消息只调用一次模型，回答与结构化操作提案一起返回（替代“路由 + 回答”两次调用，修 L1/L13/L14）；多轮上下文完整。
  - 提案以操作卡片显示（在项目 X 开对话、建定时、记住、建目标），确认后执行；每个操作有自己的回复串，可追问。
  - 项目对话、目标、定时的完成与需要处理的事项回到 Dot 作为更新；项目对话中可“发送给 Dot”。
  - 可选：Linux 托盘/快捷键打开的迷你快捷对话框。

验收：2 分钟后的定时任务按时产生未读结果（1 次真实运行）；包含两个对话的目标在检查通过后完成；“记住”的偏好在新对话中生效，遗忘后不再出现；对 Dot 说“在项目 X 里修复 Y，每天 9 点检查一次”只产生一次模型调用，确认卡片后建出对话与定时，项目对话完成后 Dot 收到更新。

### CORE.6 工程收尾（约 4–6 天，部分可穿插在前面各包中）

- 拆分 `ExecutionLedger` 为领域 Repository（对话/Run、目标、定时、记忆、工作区），共用一个数据库；打破 store ↔ runtime 循环；领域类型从 `docs/` 移到 `packages/contracts`；每个包有 `package.json` 与 `exports`，依赖方向规则进入检查。
- Smoke/探针移到测试专用入口（或 Playwright for Electron），`main.ts` 只负责组装服务与注册 IPC；锁文件、Schema 等运行资源随构建产物复制，生产代码不读仓库根目录。
- 视实测决定是否把 Store 移入 `utilityProcess`。

验收：依赖方向检查无循环；生产包不含测试代码（构建产物检查）；打包后的应用在不依赖仓库目录的情况下启动并连接。

## 5. CORE Gate：主干验收场景

在 Linux（本机）上完整走一遍；macOS 如有条件再走一遍。全部为真实组件，记录实际 Token 与结果：

1. 打开项目 → 新对话 → 问“这个项目做什么”（Agent 读代码回答）→ 追问并引用上一轮回答。
2. 另开对话，自动模式下让 Agent 修一个失败的测试：执行测试命令时弹出审批 → 允许 → 修改 → 检查命令通过 → 在右侧审阅 Diff → 撤销其中一个文件。
3. 第 2 步运行期间：浏览文件、切换对话、在另一个项目里并发问答，均无“忙”拒绝。
4. 停止一个运行中的对话，进程实际退出；重启应用后所有对话历史完整，可以继续。
5. 设定 2 分钟后向某对话发送消息的定时任务，到点出现未读结果。
6. “记住”一条偏好 → 新对话中生效 → 遗忘后不再出现。
7. 发送时强杀应用 → 重启后自动核对，不重复发送。
8. 在 Dot 里说“在这个项目里新开对话检查依赖更新，每周一提醒我”→ 确认操作卡片 → 对话与定时建出；项目对话完成后 Dot 收到更新。
9. 指标：空闲 CPU、首个 Token 延迟、窗口 Smoke 连续 5 次通过。

## 6. 测试与回归

- 日常只跑受影响范围的增量用例；全量只在用户明确要求时运行（D5：CORE.0 不跑全量）。
- 真实模型 Smoke 单独运行并记录。合成后端、Stub 与真实组件的结果分开记录。

## 7. 已确认的决策（2026-11-05）

| # | 决策 | 结果 |
